# 团队初始化与执行协议

## 1. 控制记录与工作目录

确认方案后才在选定项目根目录创建 `.project-workflows/<workflow_id>/`。workflow_id 使用日期加随机后缀；恢复以登记记录为准，不每次生成新团队。

最少保留：
- plan.md：用户确认的目标、岗位分工、流程和验收标准，记录确认依据。
- team.json：workflow_id、projectId、hostId、绝对 control_root、岗位 role_id、职责、threadId（未就绪时为空）、clientThreadId（仅暂存）、实际 cwd、初始化状态。
- state.json：当前阶段、用户是否明确开工、需求/执行编号、轮次、max_fix_rounds（默认 3）、当前工作与阻塞。
- runs/<run_id>/：每轮派单、岗位回执、报告和成果版本清单。

初始化阶段由组建者单独更新控制记录；所有角色就绪后明确移交给经理，再由经理单独管理 team/state/派单记录。成员只写自己的独立回执与成果。绝对 control_root 是唯一控制记录源，不使用各 worktree 中复制的相对路径作为状态源。运行在其他主机且控制目录不可达时停止初始化并报告，不假装共享。

状态：PROVISIONING → READY → RUNNING → REVIEW → DONE；异常进入 BLOCKED；暂停为 PAUSING → PAUSED。READY 不派发业务；DONE 之后的新需求创建新 run，保留历史。

## 2. 创建工具与两阶段初始化

使用实际可用的 Codex 工具：list_projects、list_threads、create_thread、read_thread、wait_threads、send_message_to_thread。先发现工具；缺少关键能力则说明阻塞，不用伪造任务或无关工具替代。

第一阶段：
1. 记录已批准 plan、projectId 和每个岗位的稳定 role_id，状态 PROVISIONING。首次创建任务之前，将本协议保存为控制目录的 protocol.md，并写好初始化 team.json（未就绪编号为空）；模板里的协议地址必须指向该文件，确保第一位成员即可读取。
2. 创建之前为该岗位登记创建意图和唯一 role_key = workflow_id:role_id。
3. create_thread 的 target 为 project，使用已验证 projectId；Git 默认 environment.type=worktree，非 Git 为 local。标题为岗位名，初始 prompt 包含唯一 role_key、绝对控制路径、完整本角色职责和“初始化待命，不执行项目，不派单”。
4. 每次创建立即持久化返回结果。若仅返回 clientThreadId，不把它传给要求 threadId 的接口。用任务列表及必要的 read_thread 匹配 projectId、role_key 和初始化消息，等待真实 threadId 和工作目录。
5. 创建超时/结果不明时，先搜索已存在任务并读取 role_key；不要盲目重试。同名但 role_key 不符不重用。确实未创建才补建；证据仍不明则 BLOCKED，保留已创建团队，不删任务。

第二阶段：
1. 所有真实 threadId、cwd 和 manager_thread_id 齐备后冻结映射版本，将协议及填好的角色说明放入控制目录。
2. 给每个角色发送带映射版本的“配置就绪检查”，要求核实自己的身份、职责、控制目录可读写性和成果交接方式，写独立 ready 回执，仅待命。
3. 使用 wait_threads 等待结果并复核回执；单次等待不超过 60 秒，携带 cursor 避免重复输出。不能把创建接口成功当作岗位已就绪。
4. 全部检查通过才写 READY，并明确移交经理；交付给用户。任何角色失败则保持 PROVISIONING 或 BLOCKED，列出缺失项。初始化消息不得触发业务执行。

不得向正在执行其他工作流的任务注入新角色。已匹配且处于 READY 或已开工的团队，重复组队请求只返回现状；处于 PROVISIONING 或初始化 BLOCKED 的团队，核实已完成创建与回执后续接缺失步骤，不重复创建。无法消除的阻塞据实汇报。岗位增删先更新方案并取得用户确认。

## 3. 运行与交接

用户明确开工后，经理记录授权、run_id 和验收标准，按已批准依赖图派单。所有成员将完成或阻塞结果回传经理，只有经理决定下一步与返工，避免多方同时调度和循环互等。独立工作可并行；同一成果有且只有一个写入者，验收时冻结版本。

派单最少包括 workflow_id、run_id、任务/阶段标识、round、handoff_id、目标 role_id、输入绝对路径和版本、预期成果、验收标准、经理任务地址。handoff_id 包含工作项标识，例如 workflow:run:work_item:round:role，不能仅用角色和轮次以免同一角色多项工作碰撞。

经理发送前写派单 pending；成功后写 sent。收件人处理前核实当前 run、阶段、角色、轮次和暂停状态，写 started 回执。交付写 completed、成果路径及版本、实际验证结果，再向经理发送一次回传。重复 handoff_id 已完成时只引用原交付；已开始则核实运行，不重复执行。过期消息记录忽略原因。发送结果不明先读目标任务和回执核实，无法核实则阻塞；此流程降低重复风险，不宣称分布式严格 exactly-once。

经理以验收者的证据决定：通过则推进/完成；不通过则分析实现缺陷或需求缺失，写清修复单，再重新执行受影响步骤及验收。禁止通过降低标准把失败改成通过。第 0 轮后最多追加 3 轮修复；同一阻塞连续两轮未消除则提前 BLOCKED；外部依赖不能靠重试解决时立即 BLOCKED。输出已完成项和剩余工作，不扩大需求或自行提高轮次上限。

## 4. 成果与代码同步

控制记录可共享不代表代码自动同步。派单和验收必须指定实际成果位置和版本。

- 非 Git：在共享目录按职责隔离输出，冲突写入串行。交付为文件清单及 SHA256；验收前后比对被验收成果，排除控制目录、依赖和缓存。变化则验收失效，回经理重新冻结。
- Git worktree：登记每个角色真实 cwd。开发先保留已有变更，针对本次授权修改形成可追溯提交时只暂存本次文件，禁止顺带提交用户修改；不能安全提交则阻塞同步并报告。交付包含仓库身份、commit SHA、变更文件、运行方法。验收者在干净且可隔离的工作树检出该提交或使用独立验收 worktree，不假设它已存在于默认分支。多个实现分支由经理指定唯一集成人，在干净工作树集成并重新提交供最终验收；不得自动合并主分支或推送。
- 文档/数据/图片：使用明确的绝对成果路径或可访问资源标识及版本/哈希，不只发口头摘要。控制目录中集中保存必要交接副本，避免成果留在别人无法访问的工作目录。

## 5. 暂停、恢复与运行限制

暂停时经理写 PAUSING、停止新派单并通知正在运行的岗位；成员在安全边界保存成果并回执。全部活跃岗位确认后才 PAUSED，不能用消息发送成功声称强制终止。失败或无法联系记录实际状态。

恢复时先读取最新 state、角色回执、任务状态和版本清单；确认外部阻塞解除或仍存在。只续接未完成工作；旧消息不能重新打开已完成轮次。用户明确改变范围或标准时保留变更记录并重新安排受影响验收。

工具错误、额度、应用退出或机器休眠可能中断。保存可恢复交接点；不默认安装定时任务、后台脚本或循环唤醒。无法主动恢复时告知用户发送“恢复协作”。
